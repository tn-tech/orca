# Plan research: orchestration engine internals (part 1)

Short answer: no typed service API for orchestration. Every verb is an RPC handler; authority comes from a coordinator terminal. `resolveRunScope` and `worker-start` look up a Run by the caller's live terminal pane. An engine with no terminal cannot mutate a Run through the handlers today. A legacy in-process `Coordinator` loop exists (polls every 2s, reads Tasks from every Run). SQLite `SCHEMA_VERSION = 41` (`src/main/runtime/orchestration/db/contract-constants.ts:21`).

## A.1 In-process API
- Each verb: `defineMethod({ name, params, handler })`, handler `(params, ctx: RpcContext) => result`; collected in `src/main/runtime/rpc/methods/orchestration.ts` as `ORCHESTRATION_METHODS`.
- Files: workerStart `rpc/methods/orchestration/worker/workers.ts:19` -> `startLocalWorker` (`worker/local-worker-start.ts`) or `startFederatedWorker` (`federation/federated-worker-start.ts`); taskCreate/taskList/taskUpdate/reply/inbox `messaging/message-methods.ts` (145/181/219/24/132); check `messaging/check-methods.ts:17` -> `checkRunMailbox` (`check-run.ts`), `check-worker.ts`, `check-direct.ts`; send `messaging/send-methods.ts:25`; ask `messaging/ask-methods.ts:11`; gateCreate/Resolve/List + legacy run/runStop `gates/gates.ts`; workerRead/Show/Abandon `worker/worker-control.ts` (80/27/200); workerRelease/Retain/TerminalUserInput `worker/worker-release.ts`; workerStop `worker/worker-stop.ts:17`; runCreate/Use/Current/List/Show `runs/runs.ts`; dispatch/dispatchShow `runs/dispatch-methods.ts`.
- Two ways to call from main:
  1. Through the dispatcher (precedent `src/main/ipc/runtime.ts:69`, `src/main/ssh/ssh-remote-orca-cli.ts:107`): `new RpcDispatcher({ runtime, methods: ALL_RPC_METHODS }).dispatch({ id, authToken: 'desktop-ipc', method, params, orchestrationRequestId?, orchestrationCapability?, orchestrationCompatibilityEvidence? }, { clientId, clientKind: 'runtime', connectionId, clientCapabilities, signal })`. `orchestrationRequestId` enables durable mutation receipts (`rpc/orchestration-mutation-executor.ts:58-59`); federated `--on` worker start REQUIRES it.
  2. Directly on the DB: `runtime.getOrchestrationDb()` -> `OrchestrationDb` (`src/main/runtime/orchestration/db.ts`), mixin methods: `createRun({objective, coordinatorHandle, coordinatorPaneKey})`, `bindRun`, `createTask({spec, taskTitle?, displayName?, deps?, parentId?, createdBy..., runId})`, `getTask`, `listTasks({status?, ready?, runId?})`, `listTasksWithDispatch`, `updateTaskStatus(id, status, result?)`, `createGate({taskId, question, options?, requester?})`, `resolveGate`, `timeoutGate`, `listGates`, `getGate`, `createStartingWorkerDispatch`, `insertMessage`, `getUnreadMessages(handle, types?)`, `markAsRead`, `getOrCreateRunDelivery`, `acknowledgeRunDelivery`, `getQuestion`, `answerQuestion({messageId, runId, consumerGeneration, body})`, `settleWorkerReport`. Direct DB calls skip handler-side checks (Run authority, federation relay, `notifyMessageArrived`).

## A.2 Coordinator authority
- `resolveRunScope` (`rpc/methods/orchestration/runs/run-scope.ts`) guards taskCreate/taskUpdate/gateCreate/gateResolve/reply/check: needs `callerTerminalHandle` -> `runtime.getTerminalPaneKey(handle)` -> `db.getCurrentRunForPane(paneKey)`; errors `run_required`, `stable_pane_required`, `consumer_fenced`. `requireCurrentConsumer` true for every mutation.
- Run binding: `runs.coordinator_handle`, `coordinator_pane_key`, `consumer_generation`. `createRun` (`db/runs/run-create.ts`) calls `unbindOtherRunsForPane(paneKey)` (bumps generation, fences deliveries); `runUse` -> `bindRun` (`db/runs/run-binding.ts:140`). Deliveries/answers carry consumerGeneration (`run-delivery.ts:12` rejects mismatch).
- `workerStart` stricter (`worker/workers.ts`): `resolveOrchestrationCaller(runtime, {callerTerminalHandle: params.from})` -> pane -> run; also `resolveDispatchCallerWorktreeId(runtime, params.from)` (so `from` must be a real terminal); creator via `resolveDispatchCreator`.
- Engine with no terminal: via RPC handlers NO; via DB YES (`db.createRun({coordinatorHandle, coordinatorPaneKey})` accepts any strings; createTask/updateTaskStatus/createGate/resolveGate take no caller identity).
- Legacy in-process coordinator exists: `src/main/runtime/orchestration/coordinator.ts` `class Coordinator(db, runtime: CoordinatorRuntime, {spec, coordinatorHandle, pollIntervalMs=2000, maxConcurrent=4, worktree?, onLog?})`; started by `orchestration.run` (`gates/gates.ts:25-62`), module-level `activeCoordinator`, one at a time, writes `coordinator_runs` table. `tick()`: processMessages -> reblockTasksWithPendingGates -> warnStaleDispatches -> dispatchReadyTasks (`dispatchTaskToWorker` in `coordinator-task-dispatch.ts`, `sendTerminalAgentPrompt`) -> evaluateDagConvergence. `db.listTasks()` with no runId (sees all Runs). Runtime contract `coordinator-runtime-contract.ts`: sendTerminalAgentPrompt, listTerminals, createTerminal, waitForTerminal, probeWorktreeDrift, getTerminalPaneKey?, getNestedWorkerMaxDepth?, getOrchestrationDispatchAuthority?, getTerminalOrchestrationCliCommand?.

## A.3 Message wake-up
- `RuntimeMessageWaiters` (`src/main/runtime/runtime-message-waiters.ts`): in-memory `Map<handle, Set<waiter>>`; `wait(handle, {typeFilter?, timeoutMs?, signal?, exclusive?}) -> 'notified'|'timed_out'|'cancelled'|'waiter_exists'`; default timeout `ORCHESTRATION_MESSAGE_WAIT_DEFAULT_TIMEOUT_MS` = 2 min; wakes on notify, no polling.
- Wake path: `runtime.notifyMessageArrived(handle, type)` (`orca-runtime-refresh-floating-workspace-pty-liveness.ts:195`) -> `OrchestrationMailboxNotificationCoordinator.notifyMessageArrived` (`orchestration/mailbox-notification-coordinator.ts`): resolves waiters; else queues `deliverForHandle` (pointer typed into pane, or structured-session lane). `run:` and `dispatch:` handles are mailbox addresses.
- `check --wait` (`check-run.ts`): route direct mail -> `getOrCreateRunDelivery({runId, consumerGeneration, wakeTypes})` -> else `await runtime.waitForMessage('run:<id>', {typeFilter, timeoutMs, signal, exclusive:true})` (second waiter gets `waiter_exists`) -> re-check generation.
- Callers of notifyMessageArrived: ask (`run:<id>`), reply (`dispatch:<id>`), send, worker-exit escalation (`orca-runtime-subscribe-to-terminal-resize.ts:138`).
- No EventEmitter/pub-sub for message insert. An engine holding `waitForMessage('run:<id>')` would collide with a CLI coordinator `check --wait` on the same Run (exclusive per handle).
- Unverified: pointer delivery for a Run whose coordinator pane has no live pane.

## A.5 Lifecycle
- `db/lifecycle-transition.ts`: Task any->any; Dispatch pending -> dispatched|completed|failed|circuit_broken; Worker graph starting|ready|start_unknown|stopping|stop_unknown|succeeded|failed|stopped|abandoned.
- `updateTaskStatus` (`db/tasks/task-status-transition.ts`): refuses completed/failed while supervised worker active (task_not_startable); refuses dispatched without active Dispatch; terminal status -> `settleActiveDispatchesForTask`; completed -> `promoteReadyTasks(id)` same txn.
- Readiness: createTask sets ready iff all deps completed (SQL CASE over json_each); `promoteReadyTasks` scans all pending tasks (no Run filter). Failed dep does NOT cascade (dependents stay pending forever).
- Circuit breaker `DISPATCH_CIRCUIT_BREAK_FAILURES = 3` (`db/dispatch-context/dispatch-circuit-breaker.ts`); `dispatch-completion.ts:153`. worker-start insert (`db/dispatch-row-writer.ts`) does not carry failure_count forward (defaults 0).
- `--retry-of` (`db/worker-dispatch/worker-dispatch-start.ts:92-116`): prior Dispatch must be the task's latest, worker state failed|stopped|abandoned, Task status failed|blocked -> dispatched. Without retryOf Task must be ready. retryOf + spec forbidden.
- Gates (`db/decision-gates/decision-gate-store.ts`): createGate throws while supervised worker active; else inserts, `completeActiveDispatchesForTask`, Task -> blocked. `resolveGate` auto `updateTaskStatus(task, 'ready')` (no reject path). `timeoutGate` marks only. Legacy loop `reblockTasksWithPendingGates`.

## A.6 Depth and concurrency
- `src/shared/nested-worker-depth.ts`: default max depth 1, root depth 0, code `nested_worker_depth_exceeded`; setting `nestedWorkerMaxDepth` (renderer-writable only, omitted from SettingsUpdate RPC). Depth via `resolveChildDispatchDepth` in `createStartingWorkerDispatch`.
- No global concurrency cap on worker-start; only legacy Coordinator maxConcurrent 4. One active Dispatch per assignee handle/pane (`DISPATCH_CONTEXT_CLAIM_SQL`).

## A.7 Federation
- `params.on` -> `startFederatedWorker` -> `runtime.resolveOrchestrationWorkerServer(on)` -> `callOrchestrationWorkerServer`. Requires orchestrationRequestId; exact remote worktree or new-top-level ('current'/'new-child' rejected); always terminal agent.
- Run/Task/Dispatch rows stay in home DB + `federated_dispatches`; remote keeps `remote_dispatch_attachments`; messages via `federation_relay_items`. SSH: orchestration state client-resident; `ssh-remote-orca-cli.ts` builds RpcDispatcher on client.

## B.8 worker-start params and preamble
- Params: task|spec (exactly one), taskTitle, deps, parent, on, run, from (required), worktree ('current' default | 'new-child' | 'new-top-level' | selector), name, repo, baseBranch, displayName, comment, setup run|skip|inherit, terminal, agent, model, effort, retryOf (requires task), timeoutMs, devMode. Persisted to `worker_dispatches.start_options`.
- Preamble `src/main/runtime/orchestration/preamble.ts` `buildDispatchPreamble({taskId, dispatchId, dispatchCapability?, taskSpec, coordinatorHandle, workerHandle, devMode?, cliCommand?, baseDrift?, workerKind?: 'prompt-returning-agent'|'bare-shell', canDispatchSubWorkers?})`: coordinator handle, task ID, CLI-only; recipes for worker_done (once, 3-sentence, --files-modified/--report-path), heartbeat every 5 min (stale 10 min), ask --timeout-ms 600000 ("NEVER use AskUserQuestion"), escalation, check at checkpoints; "AFTER worker_done"; optional BASE DRIFT / SUB-DISPATCH; ends `=== TASK ===\n${taskSpec}`. ## B.9 worker_done and worker-read
- Payload built by CLI `src/cli/handlers/orchestration/message-payload.ts` JSON `{taskId, dispatchId, outcome, filesModified[], reportPath, phase}`; RPC callers pass payload JSON string in SendParams.
- Settlement `reconcileLifecycleMessage` (`lifecycle-reconciliation.ts:204-306`): requires taskId, dispatchId, outcome, sender authority; writes `tasks.result` via `settleWorkerReport` as JSON `{provenance:'worker_report', outcome, messageId, reportedBy, subject, body, completedBy, filesModified, reportPath, completedAt}`.
- `orchestration.workerRead` (`worker/worker-control.ts:80`) params `{dispatch, cursor?, limit?, source?}`; federated -> federated reader; released -> archive (`readArchivedWorkerOutput`); else `readStructuredWorkerOutput` or `readExactWorkerOutput`. Archive kinds transcript_pin, terminal_tail (262,144 chars), structured_journal.

## B.12 ask / reply
- Timeouts `src/shared/orchestration-ask-timeout.ts`: default 600s, max 1800s, grace 5s.
- ask: requires active Dispatch for from/pane; `db.createQuestion` -> question_threads row + 'question' message to `run:<id>` + notify; loops `waitForMessage('dispatch:<id>')` until answered/closed/timeout; returns `{answer, messageId, answerMessageId, threadId, timedOut, cancelled, connectionLost, timeoutMs}`; `--resume <id>`.
- reply: `resolveRunScope(requireCurrentConsumer)`; `db.answerQuestion({..., consumerGeneration})`; notify `dispatch:<id>` or federation relay.
- Nothing in desktop or mobile UI shows questions/gates. Renderer/mobile call only `orchestration.dispatchShow` and `orchestration.workerTerminalUserInput`.
- Structured-session `respondToQuestion`/`respondToApproval` take `{envelope, itemId, expectedRevision, optionId}` (option id, no free text; journal question items carry `freeTextQuestionId?`).

## RISKS (from agent)
1 authority tied to terminal (own pane / direct DB / new principal); 2 engine fenced if user run-use/run-create on same pane; 3 wake-up fragile (waitForMessage in-memory, lost on restart, exclusive per handle; turn completions live-only) -> read DB backlog first; 4 legacy Coordinator not Run-scoped, promoteReadyTasks cross-Run; 5 no task edit/delete/metadata -> migration v42 or new tables; 6 failed dep leaves dependents pending; gateResolve always -> ready (no reject); createGate refuses while worker active; timeoutGate doesn't touch task; 7 circuit breaker may not cover worker-start path; retry-of strict preconditions; 8 results unstructured (no JSON schema anywhere); 9 prompt extension only via spec (`assertWorkerStartTaskSpecWithinPromptBudget`); 10 no UI for questions/gates; 11 federation/SSH need orchestrationRequestId + exact worktree; client-resident state; 12 skills.install needs content-addressed package; CLI path only bundled skills via npx skills add; nothing writes info/exclude; plugins not installable.
