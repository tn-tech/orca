# Visual DAG / Node-Graph Workflow Editor for Orca — Product Research Report

*Research date: 2026-09-23. Sources are 2025–2026 unless noted.*

---

## 0. The single most important finding: Orca already has half the engine

Before looking outward, the codebase itself changes the framing. Orca ships an **experimental orchestration runtime** (`src/main/runtime/orchestration/`, `skill-guides/orchestration.md`) with:

- **Run → Task → Dispatch** model. `TASK_STATUSES = ['pending','ready','dispatched','completed','failed','blocked']` (`src/main/runtime/orchestration/db/lifecycle-transition.ts`). Tasks carry `deps` (editable via `task-update --deps`, PR #7578); readiness is recomputed when deps complete; a **circuit breaker** trips after repeated dispatch failures (`coordinator-task-dispatch.ts` → `status === 'circuit_broken'`); nested workers obey a **depth limit** (`nested_worker_depth_exceeded`, `db/dispatch-depth.ts`).
- **Decision gates**: `gate-create --task <id> --question --options <json>`, `gate-resolve --id --resolution`, `gate-list` (`skill-guides/orchestration/references/messaging-and-gates.md`). A coordinator-owned human/LLM decision on a DAG task; the task flips to `blocked` while the gate is open. Doc rule: "Do not create a gate merely to answer a worker's `ask`."
- **Structured worker results**: `worker_done --outcome succeeded|failed --files-modified --report-path` plus a three-sentence summary; `ask`/`reply` (blocking question), `escalation`, heartbeats; group addresses `@all`, `@idle`, `@claude`, `@codex`, `@opencode`, `@gemini`, `@droid`, `@grok`, `@cursor`, `@worktree:<id>`.
- **Canonical supervised loop** (skill guide): `run-create` → N × `worker-start --spec --worktree current|new-child --agent <cli>` → `check --wait --types worker_done,escalation,question` → reply/release/ack → repeat. Guidance: "prefer parallel waves over chains deeper than three or four steps."
- **Automations** (`src/shared/automations-types.ts`): `AutomationRunTrigger = 'scheduled' | 'manual'` — a cron-prompt runner, not a pipeline.
- **Verdict vocabulary** for liveness: `live` / `unverifiable` / `exited`; "contact loss is not process death" (SSH boundary).
- **No graph rendering** in the renderer today (only `mermaid` for markdown preview; `AgentsOrchestrationVisual.tsx` is a marketing feature-wall). No `@xyflow`, `dagre`, or `elkjs` dependency in `package.json`.

## 1. Agent-workflow builders

### LangGraph / LangSmith Studio
- **(a) Model:** `StateGraph` of Python/JS node functions sharing one typed state; edges are normal, conditional (router returns node name(s) or a mapping `{True: "b", False: "c"}`), or dynamic `Send(node, state)` for map-reduce. `Command(update=…, goto=…)` merges a state write with routing in one return. ([graph-api](https://docs.langchain.com/oss/python/langgraph/graph-api))
- **(b) Cycles:** cycles are first-class. Bounded only by `recursion_limit` (counts *supersteps*; 25 in older docs, quoted as 1000 on the current graph-API page) → `GraphRecursionError`. Nodes can read `config["metadata"]["langgraph_step"]` to self-terminate. ([GRAPH_RECURSION_LIMIT](https://docs.langchain.com/oss/python/langgraph/errors/GRAPH_RECURSION_LIMIT), [cycles & limits](https://machinelearningplus.com/gen-ai/langgraph-cycles-recursion-limits-agent-loops/), [1.0.6 infinite loop bug](https://github.com/langchain-ai/langgraph/issues/6731))
- **(c) Fan-in:** Pregel supersteps — all parallel nodes in a superstep finish, then **reducers** merge their writes (`Annotated[list, operator.add]`). Uneven branch lengths need `defer=True` on the join node, which waits until "no more non-deferred work can run", *not* "all my ancestors" — a documented foot-gun ([issue #6005](https://github.com/langchain-ai/langgraph/issues/6005), [join dropped when a branch is skipped #2666](https://github.com/langchain-ai/langgraphjs/issues/2666), [deferred nodes](https://changelog.langchain.com/announcements/deferred-nodes-in-langgraph), [Medium walkthrough](https://medium.com/@gmurro/parallel-nodes-in-langgraph-managing-concurrent-branches-with-the-deferred-execution-d7e94d03ef78)).
- **(d) State:** one shared state object, per-key reducers; checkpointed every superstep.
- **(e) HITL:** `interrupt()` inside a node; resume with `Command(resume=value)` ([interrupt bug #792](https://github.com/langchain-ai/langgraphjs/issues/792)).
- **(f) Per-node config:** each node is code; model choice is whatever the node calls.
- **(g) Run viz:** Studio v2 is browser-only (early 2026); Graph mode shows traversed nodes and intermediate state; **time-travel**: rewind to any checkpoint, edit state, fork a new run; Chat mode for business users. ([LangSmith Studio](https://docs.langchain.com/langsmith/studio), [mem0 guide](https://mem0.ai/blog/visual-ai-agent-debugging-langgraph-studio), [buildmvpfast](https://www.buildmvpfast.com/blog/langgraph-cloud-ga-visual-debugging-agent-studio-2026))
- **(h) File:** code, not a graph file. **(i) Canvas:** Studio is closed-source.

### Dify (open source)
- **(a)** Node canvas: Start, LLM, Agent, If/Else, Iteration, **Loop**, Code, Variable Assigner, HTTP, Human Input, etc.
- **(b) Loops:** a **Loop container node** (v1.2, 2025) with loop variables, an exit condition expression (`quality_score > 0.9`), a **Maximum Loop Count** hard cap, and an explicit *Exit Loop* node. Loop = stateful sequential refinement; **Iteration** = stateless parallel for-each. ([Loop docs](https://docs.dify.ai/en/use-dify/nodes/loop), [PR #14863](https://github.com/langgenius/dify/pull/14863), [announcement](https://x.com/dify_ai/status/1903011106022625554))
- **(c)** Parallel branches (v0.8): simple, nested, iterative, conditional; branches rejoin implicitly. ([parallel branch](https://dify.ai/blog/accelerating-workflow-processing-with-parallel-branch))
- **(d)** Named variables referenced as `{{#node.output#}}`; loop variables persist across iterations and become the loop's output.
- **(e)** **Human Input node** (v1.13, 2026): pauses, sends a form to a designated person, decision buttons pick the outgoing branch. Not yet allowed inside Loop containers ([#32453](https://github.com/langgenius/dify/issues/32453)). ([blog](https://dify.ai/blog/the-human-input-node-bringing-human-judgment-into-automated-workflows))
- **(f)** Per-LLM-node model + params. **(g)** Live node status on canvas, per-node input/output/tokens panel. **(h)** DSL export/import (YAML). **(i)** `reactflow` v11 + `elkjs` (verified in `web/package.json`).

### Flowise Agentflow V2 (open source)
- **(a)** 15 node types incl. Agent, LLM, Condition (deterministic operators), **Condition Agent** (LLM-routed to named scenarios), Human Input, **Loop**, Iteration, Execute Flow (sub-flow with overrides), Custom Function, HTTP, Retriever, Direct Reply, Sticky Note. ([docs](https://docs.flowiseai.com/using-flowise/agentflowv2))
- **(b)** Loop node "redirects execution backward to a previously executed node" with a **max loop count (default 5)** — a *back-edge with a cap* on an otherwise acyclic canvas ([improve loop node #4653](https://github.com/FlowiseAI/Flowise/issues/4653)).
- **(c)** Node-dependency + execution-queue model ([DeepWiki](https://deepwiki.com/FlowiseAI/Flowise/3.2-agentflow-execution)); no explicit join semantics documented.
- **(d)** `$flow.state` key-value store; keys must be declared in Start; nodes write via "Update Flow State".
- **(e)** Human Input: proceed/reject + feedback text appended to output; Agent nodes can require approval before tool calls ([HITL tutorial](https://docs.flowiseai.com/tutorials/human-in-the-loop)). Known bug: Iteration after Human Input loses session ([#5233](https://github.com/FlowiseAI/Flowise/issues/5233)).
- **(h)** JSON chatflow export. **(i)** `reactflow` v11 (verified).

### Langflow (open source)
- Loop component iterates a list and aggregates results to a "Done" port; **If-Else is incompatible with Loop** ("redesign your flow to process conditions before the loop") — a limitation to avoid. Run Flow component chains flows and can be attached as an agent tool. ([Loop](https://docs.langflow.org/loop), [Run Flow](https://docs.langflow.org/run-flow), [conditional routing issue #3858](https://github.com/langflow-ai/langflow/issues/3858)). ### n8n
- AI Agent node wraps LangChain tools/memory/output parsers ([guide](https://www.bluehost.com/blog/n8n-ai-agent-node-guide/)). Loops: **Loop Over Items** (batch), or drawing an edge back into an earlier node (n8n allows cycles; guard with IF). **Merge node** = fan-in: waits for *all* inputs by default; a zero-item branch **stalls the merge forever** unless "Only One Input" is enabled — a classic fan-in trap; modes Append / Combine / Choose Branch. ### Rivet (Ironclad, open source)
- **(b)** The cleanest answer to "DAG forbids cycles": the **Loop Controller** is *"the only node in Rivet that is allowed to contain cycles of nodes, including itself."* It has (input, default) pairs = loop-carried state, a **Continue** boolean port, a **Break** output emitting the accumulated array, and **Max Iterations (default 100) → error**. ([Loop Controller](https://rivet.ironcladapp.com/docs/node-reference/loop-controller), [control flow](https://rivet.ironcladapp.com/docs/user-guide/control-flow))

### CrewAI Flows
- Decorators: `@start`, `@listen(step)`, `@router` (returns a string label routed to `@listen("label")`). **Fan-in:** `or_(a, b)` = fire on *any*; `and_(a, b)` = fire on *all*. Cycle bookkeeping had bugs ([#6710](https://github.com/microsoft/autogen/issues/6710), [#6716](https://github.com/microsoft/autogen/issues/6716), [#6643](https://github.com/microsoft/autogen/issues/6643)). ([GraphFlow docs](https://microsoft.github.io/autogen/stable//user-guide/agentchat-user-guide/graph-flow.html), [concurrent execution PR #6545](https://github.com/microsoft/autogen/pull/6545)). ## 2. Coding-agent orchestration (the closest analogues)

### Claude Code — three distinct layers, each relevant
**Workflows (dynamic workflows)** — [docs](https://code.claude.com/docs/en/workflows). Exactly the shape #15012 copies:
- A JS script with `meta {name, description, phases}`, `agent(prompt, {schema, label, model, effort})`, `pipeline(list, fn)`, `parallel(thunks)` (barrier = wait-all), `phase()`, `log()`, `args`. Doctrine: "Who holds the plan: **the script**", vs subagents/teams where Claude decides turn by turn; "intermediate results live in script variables".
- **Loops:** plain JS `while` — e.g. "keep fixing until tsc passes or two rounds in a row make no progress". No engine cap on iterations; caps are **1,000 agents/run**, 16 concurrent by default (`CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` up to 256), 4,096 items per `parallel/pipeline`.
- **Results:** `schema` → validated JSON, retried up to 5× (`MAX_STRUCTURED_OUTPUT_RETRIES`); self-contradictory schemas rejected before start; a stopped/errored agent resolves to `null` (hence `.filter(Boolean)`).
- **HITL:** *none mid-run* — "for sign-off between stages, run each stage as its own workflow". Approval only at launch (phase list + "View raw script"; per-project "don't ask again").
- **Replay/resume:** `Date.now()`/`Math.random()` throw so a relaunch replays deterministically; completed agents return cached results; the first divergent prompt and everything after re-runs; a failed agent re-runs plus everything started after it.
- **Files:** `.claude/workflows/<name>.js` (project, shared via git) or `~/.claude/workflows/`; project wins on clash; nearest `.claude/workflows/` in a monorepo; plugins namespace `/plugin:name`; `args` passed as structured data.
- **Run UI:** `/workflows` — phases with agent count/tokens/elapsed; drill into agent (prompt, tool calls with state, result, agent's own task list); keys `p` pause, `x` stop, `r` restart agent, `s` save, `f` filter by status; "Large workflow" warning at >25 agents or >1.5M projected tokens; usage-limit pause/auto-continue; size guideline small/medium/large.
- **Prompt-cache fan-out stagger** (siblings with same model/effort/tools/schema/cwd share prefix) — a per-node config detail that affects cost.

**Agent teams** — [docs](https://code.claude.com/docs/en/agent-teams). Lead + peer sessions; **shared task list with dependencies** (pending / in progress / completed; blocked until deps complete; claiming uses file locks); mailbox JSON at `~/.claude/teams/{team}/inboxes/`; teammates message each other; plan-approval gating when the lead is in plan mode; **hooks as quality gates** (`TeammateIdle`, `TaskCreated`, `TaskCompleted` — exit code 2 = reject and send feedback, i.e. the dev→QA loop primitive). Split panes via tmux/iTerm2 (Orca open issues on Windows panes #15751/#15503). Limits: one team per session, no nested teams, lead fixed, no session resumption of in-process teammates.

**Subagents / `.claude/agents`** — reusable role definitions (`tools`, `model`, `skills`, `mcpServers`, body prompt) usable both as subagents and as teammates. The natural "node type = agent definition" source.

### OpenAI Codex CLI (multi_agent_v2)
- Roles are **TOML files** in `~/.codex/agents/` or `.codex/agents/` with `name`, `description`, `developer_instructions`, optional `model`, `model_reasoning_effort`, `sandbox_mode`, `mcp_servers`, `nickname_candidates`. Tools: `spawn_agent`, `send_input`, `wait_agent`, `close_agent`, `spawn_agents_on_csv` (one worker per CSV row). `[agents] max_threads=6, max_depth=1, job_max_runtime_seconds`. `fork_turns: "all"|"recent"|"none"` — must be `"none"` for a role's model/effort override to apply. Documented **"Implement-Then-Review Loop"**: root → worker → `wait_agent` → reviewer → if findings, another worker iteration; "typically converges in 2–3 cycles"; results returned as structured JSON. Headless: `codex exec --json`; actions needing fresh approval fail and surface to the parent. Known gap: cannot spawn a TOML agent by name ([#26868](https://github.com/openai/codex/issues/26868)). ([MultiAgentV2 guide](https://codex.danielvaughan.com/2026/05/03/codex-cli-multiagentv2-custom-roles-thread-orchestration-parallel-workflows/), [TOML subagents](https://codex.danielvaughan.com/2026/03/26/codex-cli-subagents-toml-parallelism/), [official docs digest](https://codex.danielvaughan.com/2026/05/06/codex-subagents-official-docs-reference-patterns-csv-batch/), [Simon Willison](https://simonwillison.net/2026/Mar/16/codex-subagents/), [discussion #3898](https://github.com/openai/codex/discussions/3898), [Firecrawl](https://www.firecrawl.dev/blog/codex-multi-agent-orchestration))

### OpenAI Symphony (open-source spec, Apr 27 2026)
- **Issue tracker as control plane**: poll Linear on a cadence, claim issues by active state/label, one **per-issue workspace** (sanitized, persisted), run Codex app-server up to `agent.max_turns`, refresh issue state after each turn and continue on the same thread. Config in **repo-owned `WORKFLOW.md`** (YAML front matter + Markdown prompt), hot-reloaded. Retry: continuation after ~1 s on normal exit; failures `min(10000×2^(n-1), max_retry_backoff_ms)`; attempt states `PreparingWorkspace → BuildingPrompt → LaunchingAgentProcess → InitializingSession → StreamingTurn → Finishing → Succeeded|Failed|TimedOut|Stalled|CanceledByReconciliation`; claim states `Unclaimed → Claimed(Running|RetryQueued) → Released`. Concurrency `max_concurrent_agents` (default 10) with per-state overrides. **Review loop = tracker state**: success means reaching a *handoff state* (e.g. `Human Review`), not `Done`; a reviewer moving the issue back to an active state re-triggers the agent. Approval posture "implementation-defined"; user-input signals "MUST NOT leave a run stalled indefinitely". No persistent DB; restart recovery from tracker + workspaces. Reported 6× merged PRs internally. ([SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md), [OpenAI post](https://openai.com/index/open-source-codex-orchestration-symphony/), [InfoQ](https://www.infoq.com/news/2026/05/openai-symphony-agents/), [Help Net Security](https://www.helpnetsecurity.com/2026/04/28/openai-symphony-codex-orchestration-linear/))

## Design decisions the spec must make explicitly

1. **Who is the orchestrator: deterministic engine, script runtime, or LLM coordinator?** Orca has all three in flight (#11229 YAML dispatcher, #15012 JS runtime, existing LLM `coordinator` / PR #6293 Orcastrator). Claude Code's doctrine: "the script holds the plan; Claude's context holds only the answer." The brief says "an orchestrating main agent coordinates sub-agents" — the spec must say whether the main agent *is* a node (LLM router, like AutoGen's conditional edge / Flowise Condition Agent) or the *engine* (no LLM in the control path). A suggested split, but it must be chosen: the engine drives edges and the frontier (fixes #15185's idle-coordinator problem); an optional "Router (LLM)" node type makes LLM routing explicit and visible.

2. **Loop representation on a "DAG":** (i) allow back-edges on the canvas with a mandatory `maxIterations` (Flowise/n8n/AutoGen), (ii) a **Loop container / Loop Controller node** that is the *only* place cycles may exist (Rivet, Dify, Bedrock DoWhile, Blueprints' Loop Body/Completed pins), or (iii) recursion by sub-workflow self-invocation (Argo). Option (ii) keeps the outer graph acyclic (so `task-create --deps` still works and #9815's "no cycles" validation holds) and makes the cap a node property. Also decide the termination trio: iteration cap **and/or** structured exit condition on worker output **and/or** no-progress detection (Ralph / Claude "two rounds with no progress"). Rivet errors on cap; Dify exits; must pick.

3. **Fan-in semantics per join:** wait-all (GHA `needs`, Claude `parallel`), wait-any (CrewAI `or_`, AutoGen `any`), quorum/vote (Windsurf Arena, Orca #15119 Council, Claude deep-research voting), and **what a failed/skipped/`null` branch does** to the join (n8n's stalled Merge, LangGraph's dropped join, GHA `if: always()`). Needs an explicit `on-failure: fail | skip | continue-with-partial` on the join node.

4. **Worker result contract:** free-text `worker_done` summary (today) vs **JSON schema per node** (Claude `schema`, Codex, Devin children) vs repo artifacts (files/commits/PR — Symphony, Ralph, coordinator-skill). Edge conditions need something machine-readable; the spec must pick the canonical channel and how a QA node's `findings[]` reaches the developer node on the loop-back (state key? message? file in the worktree?). Also whether mechanical nodes (run tests, git) exist with zero LLM (#15012 "v1 can wait").

5. **Worktree topology per node:** same worktree (sequential dev → QA on the same branch), child worktree per node (Cursor/Conductor), or per-loop-iteration. **Write-ownership constraints** per node (coordinator-skill, Cursor's "no shared writes" inference) and how a QA node accesses the developer's worktree. Must cover folder workspaces (no git) and SSH hosts (execution host owns everything; `live/unverifiable/exited`).

6. **Where the workflow file lives and its format:** committed to repo (`.orca/workflows/*.yaml|json` like Rivet/Symphony/Claude) vs user-global vs SQLite-only; YAML vs JSON vs JS; precedence project > personal (Claude). Whether canvas positions live in the same file (n8n/ComfyUI yes; Argo/Kestra no — auto-layout). Whether it's importable from a ticket graph (#14856) or exported from an LLM decomposition (#9815). Relationship to #8896 portable presets.

7. **Human gates:** node type ("Approval" like Dify/Windmill/OpenAI) vs edge property vs reuse of Orca's task **decision gates**; whether gates work inside loops (Dify can't yet); timeout/escalation behaviour (Symphony: never stall indefinitely); where they surface (Kanban card #11378, gate strip orca-viz, notification, mobile).

8. **Per-node agent config surface:** which of {agent CLI, model, reasoning effort, skills, permission mode, MCP servers, worktree policy, prompt template with `${vars}`} are node-level vs preset/role-level (#9712) vs run-level overrides; whether `.claude/agents` / `.codex/agents` TOML / `opencode.json` agents can be *referenced* as node types instead of re-described; interactive pane vs headless one-shot per node (#15012's `{ interactive: true }`).

9. **Run semantics:** resume/replay (Claude cached agent results, Temporal history), re-run failed only vs from a node (GHA), pausing whole runs, per-node retry policy vs Orca's circuit breaker, cancelled/superseded states (#14548), and whether status transitions get timestamped so the run view isn't reconstructed (orca-viz's complaint).

10. **Triggers:** manual only vs extending `AutomationRunTrigger` (`scheduled | manual`) with events (`on_pr_opened`, `on_worker_done`, `on_gate_resolved` — #11229) or tracker-state polling (Symphony).

11. **Sub-workflows / nesting** (Rivet subgraph, Kestra subflow, ADK nested workflow, ComfyUI subgraph) vs flat graphs only, and how nesting interacts with Orca's dispatch-depth limit and "no nested teams" (Claude) / `max_depth=1` (Codex) norms.

12. **Canvas library**: `@xyflow/react` (MIT, ecosystem, orca-viz precedent) vs Rete; dagre vs elkjs-in-worker. tldraw is excluded by license.

13. **Coexistence with the LLM coordinator skill:** does a graph run bind a Run and appear in `worker-list`/`check` like any supervised Run (so orca-viz, the CLI, and mobile keep working), or is it a separate provenance record (#15012)? The agent-status store rule (one store, readers keep presentation policy) argues for the former.
